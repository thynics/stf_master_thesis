\chapter{Results}
\label{chap:results}

This chapter evaluates the CUDASTF runtime scheduler on a single-node
multi-GPU platform. It first defines the experimental platform and metrics,
then states the evaluation plan, reports the headline results, and finally
explains the main placement and DVFS outcomes in more detail.

\section{Experimental Setup}
\label{sec:results-setup}

All experiments run on a single Slurm-managed node with eight NVIDIA L4 GPUs.
The application-visible GPU set contains all eight GPUs, and power sampling is
also performed across the same eight devices. This keeps the placement and
energy measurements aligned: the scheduler can place work on any of the eight
GPUs, and the energy measurement covers the same device set.

The software environment is containerized with Apptainer. The code is built in
Release mode using CUDA 12.4.1, NVIDIA CUDA compiler 12.4.131, GCC 11.4, and
CUDA architecture 89. The benchmark executable and the power-sampling process
run inside the same containerized environment so that compiler, CUDA runtime,
and library versions remain fixed across the evaluation.

The NVIDIA L4 platform exposes application-clock control through NVML. In the
evaluated DVFS configuration, the high graphics-clock level corresponds to the
default high-performance clock observed near 2040 MHz during the kernel window.
The nominal middle graphics-clock target is 1875 MHz, and the memory clock is
kept at 6251 MHz. Each GPU has a 72 W power limit in the measured environment.
The results therefore evaluate a conservative core-frequency control path: the
runtime changes the SM clock level but does not lower the memory clock.

The evaluation uses six CUDASTF benchmarks: FDTD, CG, MiniWeather, Cholesky,
LU decomposition, and Blocked N-body. These benchmarks cover both
copy-sensitive task graphs and near-neutral task graphs, which is important for
evaluating whether a residual scheduler improves favorable cases without
forcing changes where there is little opportunity.

\section{Metrics}
\label{sec:results-metrics}

\textbf{Kernel latency.}
Kernel latency is the primary performance metric. It measures the elapsed time
between the benchmark's kernel-window start and end timestamps. This is the
appropriate latency metric for the scheduler evaluation because both placement and
DVFS decisions act on GPU task execution, not on unrelated process startup or
host-side output handling.

\textbf{Kernel energy consumption.}
Kernel energy is the primary energy metric for DVFS. It is computed from NVML
power samples collected on all visible GPUs during the same kernel window as
the latency measurement. The sampled power curve is integrated with the
trapezoidal rule, so the reported energy corresponds to the GPU energy consumed
while the benchmark kernels are active. This metric is used for the headline
DVFS result.

\textbf{Kernel power.}
Kernel power is the average NVML power over the kernel window. It is not the
headline objective by itself, because lower power can be offset by longer
runtime. Instead, it is used to explain whether an energy reduction comes from
lower average power, shorter runtime, or both.

\textbf{Whole-process energy.}
Whole-process energy integrates power over the full benchmark process rather
than only the kernel window. It captures extra effects such as startup,
initialization, host-side work, and final output handling. This thesis reports
whole-process energy only as auxiliary context. The headline energy result is
based on kernel energy because the scheduler and DVFS controller act on the GPU
execution window.

\textbf{EDP and ED\(^2\)P.}
Energy--delay product combines energy and runtime as
\(\mathrm{EDP}=E \times T\). ED\(^2\)P extends this to
\(\mathrm{ED}^2\mathrm{P}=E \times T^2\), giving stronger penalty to slowdown. These
metrics are useful for reasoning about energy--performance trade-offs, but the
main result tables report energy and latency separately so the reader can see
the trade-off directly.

\textbf{Speedup and geometric means.}
Placement speedup is computed from the ratio between HEFT latency and scheduler
latency. Suite-level placement and DVFS summaries use geometric means so that
each benchmark contributes multiplicatively rather than allowing one large
absolute benchmark to dominate the aggregate.

\textbf{Relative deltas.}
All relative results use the baseline named in the corresponding section.
For placement, the baseline is HEFT with DVFS disabled. For DVFS, the baseline
is no-DVFS execution with the same placement layer. Negative deltas in latency,
energy, power, and copy traffic indicate reductions relative to that baseline.

\textbf{Data-movement and clock evidence.}
Copy-byte reduction and non-HEFT deviation rate are used to analyze the
placement result. Average SM clock and middle-clock sample share are used to
analyze the DVFS result. These are supporting measurements: they help explain
the observed latency and energy changes, but the main claims are based on
kernel latency and kernel energy.

\section{Evaluation Plan}
\label{sec:results-plan}

The evaluation separates placement from frequency control. The placement
experiments compare HEFT with the bandit scheduler while DVFS is disabled. The
DVFS experiments hold the placement layer fixed and compare WinDVFS against a
no-DVFS baseline using kernel energy as the main metric. This isolation is
important because placement changes where work runs, whereas DVFS changes the
frequency at which the selected GPUs execute that work.

The evaluation is organized around four questions:

\begin{enumerate}
\item Does the bandit scheduler improve suite-level kernel latency relative to
HEFT on the benchmark suite?
\item Are the placement improvements consistent with reduced data movement,
rather than only measurement noise?
\item Does WinDVFS reduce kernel energy while keeping the aggregate latency
cost small?
\item Do the clock and power measurements support the DVFS energy result, and
does the controller avoid forcing changes on low-opportunity workloads?
\end{enumerate}

The following sections answer these questions in the same order. The placement
section first reports the latency and energy deltas relative to HEFT. The
data-movement section then checks whether those deltas align with copy-volume
reductions. The DVFS section reports the energy result relative to no-DVFS
execution, while the clock and power section explains why the energy reductions
appear on some workloads but not on all of them. The chapter ends with
overheads and limitations, rather than mixing diagnostic details into the main
result tables.

\label{sec:results-placement-performance}

Table~\ref{tab:results-placement-main} reports the per-benchmark placement
results. The strongest improvements appear on CG, Cholesky, and LU
decomposition. MiniWeather and Blocked N-body remain near the HEFT baseline,

freedom. FDTD improves in the aggregate but is less stable than the
linear-algebra workloads.

The locality data supports the design of the residual placement gate. When a
non-HEFT placement can reduce copy traffic while keeping the predicted local
penalty bounded, the scheduler accepts the deviation. When that opportunity is
not present, the scheduler naturally falls back to HEFT-like behavior.

The placement setting was also checked against nearby scheduler settings. The
selected bandit-scheduler setting remained the best aggregate choice in that
check, with a four-benchmark geometric-mean speedup of \(1.076371\times\)
relative to HEFT. This supports using it as the thesis placement setting.

\section{DVFS Energy Results}
\label{sec:results-dvfs-energy}

Table~\ref{tab:results-dvfs-energy} reports the final DVFS result. FDTD,
MiniWeather, CG, and LU decomposition reduce kernel energy by roughly
\(3\%\)--\(6\%\) with less than one percent latency overhead. Cholesky also
reduces kernel energy, but pays a larger latency cost. Blocked N-body remains
near neutral, which matches the placement evidence that this workload offers
little useful control opportunity.

Across the six benchmarks, the geometric-mean kernel-energy ratio is
0.970962, corresponding to \(2.904\%\) lower normalized kernel energy. The
geometric-mean latency ratio is 1.006259, corresponding to a \(0.626\%\)
latency overhead. This is the main DVFS result: guarded window-level frequency
control reduces kernel energy on this benchmark set while keeping aggregate
latency cost below one percent.

\section{Overheads and Limitations}
\label{sec:results-overhead}

The diagnostic overhead experiment indicates that compact placement logging is
close to noise-scale for FDTD and Blocked N-body, while LU decomposition shows
a visible logging cost. Compact WinDVFS control is not a pure
logging-only measurement because it also includes policy behavior and frequency
changes. For this reason, final timing and energy claims rely on the placement
and DVFS rows above rather than on diagnostic rows.

The evaluation has three main limitations. First, all results are measured on a
single eight-GPU node, so the magnitude of the results may change with GPU
generation, interconnect topology, driver behavior, and benchmark scale.
Second, FDTD is noisier than the linear-algebra workloads and should be read as
a modest locality case rather than as the strongest placement example. Third,
the DVFS conclusion is based on kernel-window energy and latency; it does not
replace a full-system power study.

\section{Results Summary}
\label{sec:results-summary}

The experimental evidence supports both layers of the proposed design. The
bandit scheduler improves geometric-mean kernel latency by \(7.146\%\) relative
to HEFT, with the largest gains appearing on copy-sensitive workloads. The
data-movement results show that these gains align with reduced copy traffic,
while neutral workloads remain close to HEFT.

WinDVFS reduces geometric-mean kernel energy by \(2.904\%\) with \(0.626\%\)
geometric-mean latency overhead. The result is not a universal claim that every
benchmark benefits from DVFS. It is a controlled result showing that a guarded
window-level DVFS layer can extract energy savings from several CUDASTF
workloads while keeping aggregate latency cost small and leaving
low-opportunity workloads near the baseline.
